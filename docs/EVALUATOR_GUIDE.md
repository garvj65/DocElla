# DocElla Evaluator Guide

This page is the shortest route through the final DocElla 1.0.0 submission.

## What to evaluate

DocElla demonstrates three related document workflows in one application:

1. **Extract** — discover and review structured data from an arbitrary supported business document.
2. **Template review** — extract a text PDF into a known schema, review the values, and regenerate a reviewed PDF.
3. **Create PDF** — complete a schema-driven form and generate an editable or flattened PDF.

The main technical focus is the boundary around AI extraction: provider output is never trusted directly. DocElla validates schemas and values locally, grounds evidence deterministically, exposes review states, and keeps PDF generation constrained to trusted templates.

## Run locally

Prerequisites: Node.js 24 and a Groq API key.

```powershell
git clone https://github.com/garvj65/DocElla.git
Set-Location .\DocElla
npm ci
Copy-Item .env.example .env
```

Add this to `.env`:

```env
GROQ_API_KEY=your-secret-key
```

Then run:

```powershell
npm run dev
```

Open `http://localhost:5173`.

Azure Document Intelligence is not required for a normal digital text PDF. It is required for scanned PDFs, images, Office documents, and HTML.

## Five-minute product walkthrough

### A. Arbitrary document extraction

1. Open **Extract**.
2. Upload a digital text PDF such as a résumé, invoice, application, report, or similar business document.
3. Click **Analyze document**.
4. Inspect the detected document type and discovered sections/fields/tables.
5. Open evidence for several values and compare it with the source preview.
6. Edit a value and observe the independent edited state.
7. Validate the reviewed result.
8. Export reviewed JSON.

What this demonstrates:

- dynamic schema discovery rather than a preconfigured document type
- provider recovery paths plus authoritative local schema validation
- schema-constrained, batched value extraction
- deterministic evidence grounding
- explicit human review rather than silent model acceptance

### B. Fixed-schema review and PDF regeneration

1. Open the fixed-schema/template review workflow.
2. Select **Job Application** or **Basic Invoice**.
3. Upload a compatible text PDF.
4. Extract and review the values.
5. Edit at least one field and validate.
6. Generate an editable PDF.
7. Generate a flattened PDF.

What this demonstrates:

- shared runtime contracts across frontend/backend
- extraction into a known schema
- trusted template selection
- reviewed values flowing into PDF generation
- editable versus flattened output behavior

### C. Direct PDF creation

1. Open **Create PDF**.
2. Select Job Application or Basic Invoice.
3. Complete the generated form.
4. Generate both editable and flattened output.

What this demonstrates:

- dynamic forms from shared document definitions
- backend submission validation
- controlled AcroForm generation without arbitrary client paths or mappings

## Reliability behavior worth noticing

Generic discovery prefers strict JSON Schema output. If the provider cannot produce the discovery object under that mode, DocElla can move through best-effort schema output and JSON Object Mode. Every discovery result still has to pass local Zod validation.

Value extraction remains stricter. DocElla generates extraction schemas from the validated discovered schema and uses bounded batches for larger documents. Each batch and the final merged result are locally validated.

The provider smoke command can isolate key/model configuration from document-specific behavior:

```powershell
npm run smoke:groq -w @docella/backend
```

It sends no uploaded document content.

## Automated verification

The same commands used by CI are available locally:

```powershell
npm run format:check
npm run lint
npm run typecheck
npm test
npm run verify:release
```

GitHub Actions additionally builds and starts the production Docker image, verifies the health endpoint and frontend, and confirms the container does not run as root.

## Privacy and security scope

DocElla is intentionally memory-only: it has no application database or object storage. Uploaded files, extracted values, and generated PDFs are not persisted by the application.

Logs are designed to exclude document content, prompts, extracted/reviewed values, credentials, generated bytes, and provider failed-generation payloads. Extraction and generation responses are non-cacheable.

For scanned/multi-format workflows, bounded content is sent to the configured OCR provider. For model extraction, bounded content is sent to the configured Groq provider. These provider calls are part of the product boundary and are documented rather than hidden.

## Deliberate non-goals

The final submission does not claim to be a multi-tenant SaaS platform. It intentionally does not include authentication, tenant isolation, persistent document storage, distributed queues, distributed rate limiting, or arbitrary user-uploaded PDF templates.

Those are production-platform concerns beyond the core problem demonstrated here: reliable document ingestion, AI-assisted structured extraction, deterministic review/grounding, and controlled PDF generation.
